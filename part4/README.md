### Production Inference & AI Explanation Pipeline
Part 4 connects the trained ChurnGuard model with a production-style inference and explanation layer.

Production Artifact Loading:
Part 4 loads the artifacts generated by Part 3:

best_model.pkl
decision_threshold.json

best_model.pkl contains the complete production pipeline, while decision_threshold.json provides the frozen prediction threshold.

The application prints:

Loaded production pipeline from '.../best_model.pkl'
Frozen decision threshold: 0.45

If the threshold file cannot be found, the code uses 0.50 as a backup threshold.

LLM Explanation Prompt:
The LLM is used only as an explanation assistant.

The system prompt instructs the LLM to explain the model's already-computed decision and not create a different label, probability, or confidence value. The response must also be valid JSON without Markdown.

The user prompt provides:

Assigned Prediction
Model Churn Probability
Model Confidence
Top Mathematical Drivers

The required response contains:

prediction_label
confidence_level
top_reason
second_reason
next_step

Raw Feature Normalization & Validation:
The application accepts the original customer feature values instead of requiring manual one-hot encoding.

Before prediction, the input is normalized:
→ Categorical text is stripped and converted to lowercase.
→ Extra spaces are removed.
→ Internet Service values are mapped to the expected categories.
→ Contract values are mapped to the expected categories.
→ Numeric features are converted to the appropriate numeric types.

The normalized data is then checked against the project's input schema and allowed categorical values


PII Guardrail:
Before the model is allowed to run, the application checks the incoming payload for personally identifiable information.

The regular-expression guardrail looks for patterns such as:

Email addresses
Phone numbers
Customer IDs
SSN-style numbers
Long card/payment-number patterns

If a matching pattern is found, the request is blocked and the classifier is not executed.

Blocked Response

prediction_label = blocked
confidence_level = low

The response instructs the user to remove identifiers and submit only the required customer features.


Model Prediction:
After the input passes the guardrails, the normalized raw features are passed directly to the saved production pipeline.

The model first produces a churn probability:
pred_prob = best_pipeline.predict_proba(input_df)[0, 1]
The frozen threshold from Part 3 is then applied:
Probability >= 0.45 → Likely Churn
Probability <  0.45 → Likely Retained

The ML model therefore determines the actual prediction. The LLM is not responsible for choosing the churn class. 

Confidence Calculation:
The application converts the model probability into a confidence category.

Probability >= 0.70 or <= 0.30 → High
Probability >= 0.55 or <= 0.45 → Medium
Otherwise                         → Low

This value is calculated by the application before the LLM explanation is requested.


Model Driver Extraction:
The application extracts the strongest contributing features from the fitted model.

For the Logistic Regression pipeline, it:

→ Transforms the raw input using the saved preprocessing step.
→ Gets the transformed feature names.
→ Calculates feature impacts using the model coefficients.
→ Ranks the impacts by absolute value.
→ Selects the top two drivers.
→ Identifies whether each driver pushes toward Churn or Retain.

These drivers are supplied to the LLM as mathematical evidence for the explanation.

LLM Request & Temperature:
The LLM request is sent using the configured API endpoint and model.

The default configuration is:

Model       = openai/gpt-4o-mini
Temperature = 0.0
Max Tokens  = 512

The temperature is passed into the API request by call_llm()

The application calls the LLM with:
process_track_c(features, temp=0.0)

during the production test cases.

LLM JSON Validation:

The application:

Raw LLM Response
       ↓
Extract JSON Object
       ↓
Parse JSON
       ↓
Validate Against Schema
       ↓
Return Structured Explanation

The required schema checks for:

prediction_label
confidence_level
top_reason
second_reason
next_step

The confidence_level must be one of:

low
medium
high

After successful validation, the application overwrites the LLM's prediction label and confidence with the values calculated by the ML system.

Fallback Handling:
The application continues to work even if the LLM does not return a usable response.

Fallback behavior is used when:
API key is missing
API request fails
No response is returned
JSON cannot be extracted
JSON cannot be parsed
JSON fails schema validation

The fallback response is created from the already-computed model prediction, confidence, and drivers

Example status values include:

Pass (Model Default / No API)
Pass (Default Used)
Pass (LLM Generated)

Test Customer Profiles:

The application contains three predefined customer profiles for production inference testing.

Case                   Customer Profile
Case #1          2 months tenure, Fiber optic, Month-to-Month, Electronic check
Case #2          60 months tenure, Fiber optic, Two year, Credit card
Case #3          24 months tenure, Fiber optic, Month-to-month, Mailed check

The complete raw feature dictionaries are defined in test_features_list.

Each case is passed through the same production function:
process_track_c(features, temp=0.0)
The terminal displays:

Status
Prediction
Confidence
Top Driver
Action Plan

Guardrail Tests:
Two additional cases verify that the application stops unsafe or invalid inputs.

PII Test

The first customer profile is modified:
PaymentMethod = user@example.com

Expected result:
PII case: Blocked (PII Detected)
label = blocked

Invalid Tenure Test
The first profile is modified:
tenure = -3

Expected result:
Invalid tenure: Rejected (Invalid Input)
label = invalid_input

These tests confirm that both PII detection and input validation happen before model prediction.



The ML model makes the prediction. The LLM explains the prediction.

The LLM receives the already-computed prediction, probability, confidence, and mathematical drivers. The application then forces the final prediction_label and confidence_level to match the ML-derived values.
